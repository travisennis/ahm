# Persist a non-decrementing task ID counter in the store

## Summary

`nextTaskID` in `internal/ahm/task_create.go` derives the next ID from the
highest parsed task ID plus the filesystem entries. In Git, deleting the
highest-numbered task file is safe because history proves the ID was used. In
the store there is no history, so the same code reissues the ID.

Persist the counter in the records root's `project.json` as `next_id`, at the
path `storePaths.statePath()` from the ExecPlan. `nextTaskID` reads the
persisted value and takes the maximum of it and the highest record present, so
an existing store self-heals upward; it then persists the incremented value as
part of the same locked read-compute-write sequence the command already holds.
Never decrease the value. Child allocation under `--parent` keeps its current
26-child limit and scan, against the same counter.

`ahm init` and `ahm store migrate` must be able to initialize the counter from
the records present so that neither path produces an ID that already exists.

## Acceptance

- A test that fails before the change: create a task, remove its file from the
  records root, create another task; the second ID is one higher than the
  removed one and the removed ID is never reused.
- The counter file is written atomically through `writeOwned` and survives a
  dry run unchanged.
- `just ci` passes.

## Comments

**2026-09-21T16:39:01-04:00** — 267d landed. The store now persists `next_id` in its `project.json` (`storePaths.statePath()`), and top-level allocation is the higher of that counter and one past the highest record present. New `internal/ahm/task_id_counter.go` holds the counter: `taskIDCounterPath`, `readTaskIDCounter`, `writeTaskIDCounter`, `persistTaskIDCounter`, `highestTaskNumber`, and the shared `higherTaskIDCounter`. `task_create.go` allocates through the counter plus the old scan and raises the counter after the record is written; `install` seeds the counter from the records present, so a store whose state file predates it recovers the numbers it has already spent. Project mode is untouched: no counter file, no extra write, no output change.

Acceptance, against this task's own criteria. The failing-before test exists: `TestHomeModeTaskIDsAreNotReissuedAfterTheNewestRecordIsDeleted` creates 001, deletes its record by hand, and requires 002; a mutation probe that drops the counter read reproduces the reuse (`create after the deletion = "001", want 002`). `TestParentIDIsNotReissuedWhileItsChildRemains` adds the case the numeric scan cannot see at all, a deleted parent whose only remaining record is `001a`, and a manual run in a scratch repository reproduced 001 being reissued without the counter. The counter file is written atomically through `writeOwned` — the store's project directory is an owned root whenever this write runs, and `TestTaskIDCounterPathIsInsideAnOwnedRoot` pins that precondition — and it survives a dry run unchanged, modification time included: `TestHomeModeDryRunTaskCreateDoesNotConsumeAnID` snapshots the whole store and requires the preview to name the ID the next real create allocates, and `TestInitDryRunDoesNotSeedTheTaskIDCounter` covers `init`. `ahm init` seeding is covered by `TestInitSeedsTheTaskIDCounterFromTheRecordsPresent` (fails with the seeding removed) and by `TestInitDoesNotLowerTheTaskIDCounter` (fails if init writes `highest+1` unconditionally, which an idempotence test alone would not catch). Self-heal from a lagging or missing counter is `TestTaskIDAllocationHealsFromTheRecordsPresent`. An unreadable state file fails the create loudly instead of reissuing a number it cannot see: `TestHomeModeTaskCreateFailsOnAnUnreadableTaskIDCounter` covers a newer store version and corrupt JSON. `just ci` passes end to end.

Judgment calls, recorded in the ExecPlan's Decision Log and Surprises. The counter covers top-level numbers only: child allocation keeps its letter scan and never consults it, so a deleted child's letter can still be reissued; this milestone fixes the child rules, and the gap is recorded with its follow-up (a per-parent suffix mark) rather than closed here. The counter is written after the record it accounts for, so a failure in between is repaired from the records instead of spending a number for a create that never happened. Every writer of the state file keeps the higher `next_id`, because `ahm store path` records the same file with no lock; a decrement would need two writers inside one read-to-rename window, which is the unlocked-state race 267a recorded for the registry, and it stays open. `ahm init` writes `project.json` in home mode for the first time and does so silently, because it is store state rather than a reconciled workflow file. The milestone text calls the file "the records root's `project.json`"; the authoritative path is `storePaths.statePath()`, one directory above the records root.

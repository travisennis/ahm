# Decide durable research metadata enforcement

## Summary

After the durable-research creation threshold is clear, decide whether ahm should keep research metadata and lifecycle guidance advisory or establish a mechanically enforced record contract with supporting commands.

## Problem

`ahm context research` currently presents a status, date, relationship, and confidence header only "when useful." Existing code can consume conventional dates for stale-inbox reporting, while indexes and manual file operations intentionally remain lightweight. Making metadata normative or adding `research create`, `promote`, or `archive` commands could improve consistency, but it could also create a file-format compatibility and migration burden disproportionate to the value.

## Decision Work

Inventory the current source of truth for research discovery, indexing, stale-note dates, status vocabulary, storage layouts, manual moves, and upgrade compatibility. Then compare at least these options:

1. Keep the current guidance-only header and manual lifecycle.
2. Require a minimal metadata contract only for durable notes while leaving raw inbox captures lightweight.
3. Add validation for a minimal contract without adding mutation commands.
4. Add focused lifecycle commands only where they enforce a settled contract and materially reduce unsafe manual work.

Evaluate compatibility with existing `.ahm/research/` and legacy `.agents/.research/` records, migration behavior, generated indexes, `status` and `doctor`, source ownership, and whether front matter or the documented plain header should be canonical. Avoid designing commands before identifying an invariant they need to protect.

If the selected option changes a durable file-format or CLI contract, create and accept an ADR before implementation and materialize separately scoped implementation tasks. Do not implement the selected option in this decision task.

## Decision: Keep guidance-only research metadata (Option 1)

### Inventory of Current Research Plumbing

**Parsing** (`internal/ahm/research_inbox.go`):
- `researchNoteDate()` parses dates from YAML front matter first, then falls back to header lines (`Updated:`, `Date:`, `Created:`), then falls back to file mtime.
- Accepts RFC3339 or DateOnly formats.
- No front matter is required — the code gracefully handles files without any metadata.

**Indexing** (`internal/ahm/indexes.go`):
- `collectMarkdownDocs()` scans research directories for `.md` files (excluding `index.md`), reads only the H1 title, returns sorted lists per bucket.
- `renderResearchIndex()` generates `research/index.md` with sections: Inbox, Investigations, Sources, Topics, Archived.
- No metadata parsing during indexing — only H1 titles.

**Validation** (`internal/ahm/validation.go`, lines 173-202):
- Only `validateResearchInbox()` exists — checks stale inbox notes against configurable threshold (default 21 days, `0` to disable).
- Emits `research_inbox_stale` warning. Does not validate metadata format, status values, or any other research metadata.

**Prime** (`internal/ahm/prime.go`):
- `primeRecentResearchAt()` collects up to 5 recent notes from all buckets, reads H1 and age, reports in session briefing.

**Config** (`.ahm/config.json` / `.agents/ahm.json`):
- Optional `research` object with `inboxStaleDays` integer. Preserved through round-trips and upgrades.

**Storage layout**: `.ahm/research/{inbox,investigations,sources,topics,archived}/` (modern) or `.agents/.research/` (legacy). Index is generated.

**Guidance** (`internal/templates/workflow/RESEARCH.md`):
- Header is advisory: "Use this header for durable research documents when it is useful."
- Status vocabulary: inbox, active, synthesized, superseded, archived.
- Confidence: low, medium, high.
- No front matter required or enforced.

### Options Compared

| Option | Description | Migration Burden | Value |
|--------|-------------|-----------------|-------|
| 1. Status quo | Keep guidance-only header, manual lifecycle | None | Maintains lightweight character |
| 2. Minimal contract for durable notes | Require front matter in topics/investigations/sources; inbox stays lightweight | Medium — existing notes need front matter | Adds consistency for durable notes |
| 3. Validation only | Validate metadata contract without commands | Medium | Adds consistency without CLI surface |
| 4. Lifecycle commands | Add `ahm research create/promote/archive` | High — commands, file-format ADR, migration | Heaviest investment |

### Decision

**Keep Option 1 (current guidance-only header and manual lifecycle).**

Rationale:
1. The current system is intentionally lightweight and works well: research notes require zero ceremony, the stale-inbox check provides the only needed lifecycle signal, and the durable-creation threshold clarified in task 240a makes guidance actionable without enforcement.
2. No evidence of confusion or inconsistency that would justify enforced metadata. The existing code gracefully handles notes with or without front matter, dates with or without headers, and falls back to mtime.
3. The guidance template (240a) now clearly states: "Use this header for durable research documents when it is useful. Raw inbox notes may be shorter." This is proportional.
4. Adding validation or commands would create migration burden for existing notes under both `.ahm/research/` and legacy `.agents/.research/` layouts without a confirmed problem to solve.
5. ADR 020 already established the read-only validation boundary — "ahm reports, but never moves, converts, or deletes a research note." Extending into metadata enforcement would break that principle without demonstrated need.
6. Task 240a stated: "Do not introduce new metadata validation, file-format requirements, or research lifecycle commands in this task. Those require a separate compatibility decision." That decision is now made: not yet justified.

### No ADR Needed

No durable file-format or CLI contract changes. This decision can be revisited if evidence of confusion accumulates — at which point Option 2 would be the proportional next step.

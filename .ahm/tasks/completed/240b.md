# Define documentation as a task delivery obligation

## Summary

Revise the embedded documentation workflow reference so agents treat documentation impact as part of delivering task work while keeping project documentation separate from ahm-managed workflow records.

## Problem

`ahm context docs` contains useful impact criteria and correctly prefers existing documents, but it is framed mainly for work already classified as documentation. It does not explicitly describe documentation as a completion concern for implementation tasks, and its preference for existing files does not say when creating a separate durable document is justified.

## Fix Direction

Update `internal/templates/workflow/DOCS.md` to:

- describe documentation as durable project truth and a task delivery obligation, not an `.ahm` artifact lifecycle;
- retain the existing behavior-based impact triggers and the rule that internal code churn alone does not require docs;
- prefer updating the canonical existing document for a subject;
- justify a new document only when durable information has no coherent existing owner or has a distinct audience or responsibility that would make insertion into an existing document misleading;
- require a new document to follow project naming, location, navigation, tone, and validation conventions;
- keep uncertainty and unfinished work in tasks, research, or ExecPlans rather than presenting it as settled project truth;
- require handoff to identify docs checked, docs changed, or the reason no update was needed.

Do not add an `ahm docs create` command or move project documentation under `.ahm/`.

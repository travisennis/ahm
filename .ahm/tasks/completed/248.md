# Fix workflow lock cleanup and heartbeat lifecycle leaks

## Problem

Three separate lifecycle defects in `internal/ahm/lock.go`:

1. **Lock leak on the stat-failure path** (`:129-133` at task creation).
   `os.Mkdir(lockPath)` succeeds, then `os.Stat(lockPath)` fails; the function
   returns an error having created the lock directory with no release closure and
   no cleanup. The repository is then locked for `workflowLockStaleAfter` (30
   minutes) with no live owner. Note: commit `239e0cb` (owner-token identity,
   tasks 195/227) removed the `os.Stat` from `tryAcquireWorkflowLock` entirely;
   the equivalent failure point is now the owner-token write, which already
   removes the created lock directory. The acceptance test below covers that
   path via the token-write seam.

2. **Quarantine directory leak**. On both
   `errWorkflowLockOwnershipLost` returns *after* the rename succeeds — the
   `os.Stat(claimedPath)` failure and the `!os.SameFile` mismatch — `quarantine`
   is never removed, leaving a `.workflow-records.reclaim-*` directory inside
   `.lock/`. The pre-rename failure path does clean up, so the omission is
   inconsistent within the same function. In the current code the post-rename
   checks live in `removeWorkflowLockIfOwned` and `reclaimLegacyWorkflowLock`
   (the legacy fallback added by the token refactor); all three post-rename
   ownership-lost returns leak the quarantine.

3. **Heartbeat outlives release** (`:155-167`). `close(heartbeatDone)` does not
   synchronize with an in-flight `os.Chtimes`, so the goroutine can touch the
   lock path once after the release closure returns. If a successor has already
   acquired the lock by then, the heartbeat refreshes *its* mtime. The effect is
   benign today — it makes a live lock look fresher, never staler — but it
   undermines the ownership reasoning that tasks 195 and 227 established.

## Relevant Files

- `internal/ahm/lock.go` — `tryAcquireWorkflowLock` (token-write failure path,
  heartbeat release closure), `heartbeatLock`, `removeWorkflowLockIfOwned` and
  `reclaimLegacyWorkflowLock` (post-rename ownership-lost returns).
- `internal/ahm/lock_test.go` — lock mechanism coverage from task 133.
- `docs/adr/001-atomic-writes-and-concurrency.md` — locking decision.

## Fix Direction

For (1), remove the created lock directory before returning the stat error (in
current code: before returning the token-write error; the `os.Stat` itself was
removed by commit `239e0cb`). For (2), remove the quarantine directory on the
post-rename error returns, matching the existing pre-rename cleanup. For (3),
join the heartbeat goroutine with a `sync.WaitGroup` inside the release closure
so no `os.Chtimes` can be in flight once release returns.

These are independent one-to-few-line fixes in one file; keep them as clearly
separated hunks so the ownership reasoning stays reviewable (separate commits
are not used: the repository rule forbids committing unless explicitly asked).

## Outcome

All three defects fixed in `internal/ahm/lock.go`; the change is single-file
plus its tests, verified with `-race` and against the pre-fix code.

1. Token-write failure path: the created lock directory is removed before the
error return (the `os.Stat` failure path no longer exists after the owner-token
refactor). Covered by `TestAcquireWorkflowLock_TokenWriteFailureRemovesCreatedLock`
using the injectable `workflowLockTokenWriter` seam.
2. Quarantine leak: `removeWorkflowLockIfOwned` and `reclaimLegacyWorkflowLock`
now remove the quarantine directory on all three post-rename ownership-lost
returns. Covered by `TestRemoveWorkflowLockIfOwned_PostRenameMismatchCleansQuarantine`,
`TestReclaimLegacyLock_StatFailureAfterRenameCleansQuarantine`, and
`TestReclaimLegacyLock_IdentityMismatchAfterRenameCleansQuarantine`, which use
the deterministic `workflowLockClaimHook` seam and assert no `.reclaim-*`
directory survives.
3. Heartbeat join: the release closure closes the done channel, waits on a
`sync.WaitGroup`, then removes the lock, so no `os.Chtimes` can be in flight
once release returns. `heartbeatLock` takes the chtimes func as a parameter
(read once per acquire from the `workflowLockChtimes` seam) to keep the seam
race-free. Covered by `TestAcquireWorkflowLock_ReleaseJoinsHeartbeat`, which
holds a heartbeat Chtimes open and proves release cannot return until it
completes.

Each new test was verified to fail against the pre-fix code and pass against
the fix. Existing stale-lock, replacement, and ownership tests (tasks 195/227)
all still pass.

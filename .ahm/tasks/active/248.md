# Fix workflow lock cleanup and heartbeat lifecycle leaks

## Problem

Three separate lifecycle defects in `internal/ahm/lock.go`:

1. **Lock leak on the stat-failure path** (`:129-133`). `os.Mkdir(lockPath)`
   succeeds, then `os.Stat(lockPath)` fails; the function returns an error
   having created the lock directory with no release closure and no cleanup. The
   repository is then locked for `workflowLockStaleAfter` (30 minutes) with no
   live owner.

2. **Quarantine directory leak** (`:239-245`). On both
   `errWorkflowLockOwnershipLost` returns *after* the rename succeeds — the
   `os.Stat(claimedPath)` failure and the `!os.SameFile` mismatch — `quarantine`
   is never removed, leaving a `.workflow-records.reclaim-*` directory inside
   `.lock/`. The pre-rename failure path does clean up, so the omission is
   inconsistent within the same function.

3. **Heartbeat outlives release** (`:155-167`). `close(heartbeatDone)` does not
   synchronize with an in-flight `os.Chtimes`, so the goroutine can touch the
   lock path once after the release closure returns. If a successor has already
   acquired the lock by then, the heartbeat refreshes *its* mtime. The effect is
   benign today — it makes a live lock look fresher, never staler — but it
   undermines the ownership reasoning that tasks 195 and 227 established.

## Relevant Files

- `internal/ahm/lock.go:129-133` — `tryAcquireWorkflowLock` stat-failure path.
- `internal/ahm/lock.go:155-167` — `heartbeatLock` and the release closure.
- `internal/ahm/lock.go:239-245` — post-rename ownership-lost returns in
  `removeStaleWorkflowLockAfterObservation`.
- `internal/ahm/lock_test.go` — lock mechanism coverage from task 133.
- `docs/adr/001-atomic-writes-and-concurrency.md` — locking decision.

## Fix Direction

For (1), remove the created lock directory before returning the stat error. For
(2), remove the quarantine directory on both post-rename error returns, matching
the existing pre-rename cleanup. For (3), join the heartbeat goroutine with a
`sync.WaitGroup` (or equivalent) inside the release closure so no `os.Chtimes`
can be in flight once release returns.

These are independent one-to-few-line fixes in one file; keep them as separate
commits or clearly separated hunks so the ownership reasoning stays reviewable.

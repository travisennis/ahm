# Document the home store across the workflow spec and CLI reference

## Summary

Consolidate the documentation and hand the release-note items to 264f. Each
earlier milestone updates the documentation it touches; this milestone makes
the whole surface consistent and checks that no page still describes the old
behavior as the only behavior.

Update:

- `docs/references/workflow-spec.md`: the store layout, project identity and
  its canonicalization, the `tasks_location` key and its default, the display
  convention, the link-resolution order, the ownership boundary with two owned
  roots, the lock and temp-cleanup location, the persisted ID counter, and the
  store format version with its refusal path.
- `docs/guides/workflow-upgrades.md`: how to opt in with
  `ahm store migrate --to home`, what to commit, what to do about the ignored
  task indexes left in the working tree (the same situation the v1 to v2 move
  created for the retired families), and how to reverse the move.
- `docs/cli.md`, `docs/references/cli/commands.md`,
  `docs/references/cli/task-commands.md`, and
  `docs/references/cli/global-contract.md`: the `store` command group, the
  `init` behavior change, the store fields in `prime` and `status` output, the
  new finding code, and `AHM_HOME`.
- `ARCHITECTURE.md`: the module map for the new files, the invariant that
  every workflow write lands under an owned root, and the second owned root in
  the system-boundaries and compatibility-surfaces sections.
- `docs/references/glossary.md`: home store, project key, records root,
  registry, mode, drift finding.
- `docs/workflow/tasks.md`: replace the storage section that says task records
  live under `.ahm/tasks/`.
- `AGENTS.md`: remove the claim that records are branch-scoped, and update the
  compatibility-surfaces sentence about atomic writes and root detection if it
  needs it. Treat this as an agent-behavior-shaping edit and follow
  `docs/guardrails/agent-instructions.md`.

Then report to 264f, in the tracker's comment or the release task's body, the
release-note items this work owes: the home store as the default for new
projects, the `tasks_location` key, the `ahm store` group, `AHM_HOME`, and the
statement that existing repositories are unaffected until they migrate.

## Acceptance

- `just docs-md-lint` passes and `just ci` is green.
- No document still claims that task records always live under `.ahm/tasks/`
  or that records are branch-scoped without naming the mode.
- The CLI reference documents every new command, flag, output field, and
  finding code.
- 264f names the storage change in its release notes.

**2026-09-21T14:36:33-04:00** — 267c decided the questions this milestone owes wording for. (1) The store's managed `.gitignore` is per project, at `<store>/projects/<slug>-<hash>/.gitignore`, listing the generated task indexes, `.lock/`, and `*.tmp`; the store root stays outside the owned roots, so `registry.json` is commit-visible derived data. The workflow-spec and upgrade guide should say that, and the plan's Idempotence paragraph was corrected. (2) Display: findings, error messages, index listings, and lock errors render `store:<store-relative>`; the JSON `path` field of a task and the dry-run create, move, and unblock previews keep the record's own path in project mode and render `store:<rel>` in home mode, because those payloads are absolute today and ADR 023 keeps project-mode output byte-identical. `ahm store path` already prints absolute store paths, which ADR 023's display rule should name as an exception. (3) New validation findings to document: `task_records_in_project` and `store_dir_unreadable` (both error tier; already in docs/references/cli/task-file-format.md). (4) A repository with no `.ahm/config.json` resolves as `project` until 267f turns the new-project default on.

**2026-09-21T15:24:05-04:00** — One more wording item from 267c's review: because commands resolve the layout in root detection, a home-mode project whose Git state cannot be read (missing `git` on PATH, or a `.git` that Git cannot read) now fails every command, doctor and status included, with the resolver's error. That is the intended alternative to deriving a different key from the path, which would split the backlog, but the guide should say a home-mode project needs readable Git state. The same applies to an operating-system error message: findings and labels render store:<rel>, while an OS error keeps its own text, which may name an absolute path.

**2026-09-21T15:35:01-04:00** — Correction to the previous comment: the store's managed .gitignore ignores the generated task indexes, `.lock/`, `*.tmp`, and `project.json` (the store state file). Also add `README.md` to this milestone's scope: it still describes task records as ordinary committed files under `.ahm/tasks/` unconditionally, which is true only for `project` mode.

The upgrade guide needs a line telling a store that already holds records to run ahm init once, so the counter is seeded before any record is deleted; 267d left that out because no released version has a store, and this milestone owns the store's upgrade narrative.

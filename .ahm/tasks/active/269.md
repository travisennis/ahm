# Serialize the store registry and project state writes

## Summary

`recordStoreProject` read-modify-writes two shared files with no lock:
`<store>/registry.json` and the store's `project.json`. Two `ahm store path`
runs in different projects, or a `store path` racing a `task create` in one
project, can lose an observation. A dropped `remotes` or `paths` entry is not
recoverable, and a state write that carries a stale `next_id` can lower the
counter that 267d made monotonic: the merge in `writeProjectState` and
`writeTaskIDCounter` narrows that window to one read-to-rename gap but cannot
close it, because neither writer holds a lock.

267a recorded this as a Surprises entry ("the registry is one file per machine,
and `recordStoreProject` read-modify-writes it with no lock ... the fix belongs
with the store lock that 267b moves into the store, or in its own task"). 267b
put the record-mutation lock beside the records, which `store path` never takes,
and 267d's ARCHITECTURE invariant names the residual hole. No task owns it yet.

## Detail

- `internal/ahm/store.go`: `recordStoreProject` (the unlocked
  read-modify-write), `loadRegistry`, `writeRegistry`, `readProjectState`,
  `writeProjectState`, and `writeStoreFile`.
- `internal/ahm/task_id_counter.go`: `writeTaskIDCounter`, which writes the same
  state file through `writeOwned` while `task create` holds the record lock.
- Existing lock helpers: `acquireNamedWorkflowLock` and
  `withWorkflowRecordLock` in `internal/ahm/lock.go`; the record lock root is
  `workflowPaths.lockDir()`.
- Decide the lock's scope. `registry.json` is machine-wide and sits at the store
  root, which is deliberately outside the owned roots, so a store-level lock is
  the smaller answer; the constraint is that it must not deadlock with the
  per-project record lock a `task create` holds while it writes the state file,
  and that a lock directory under the store root must not break the
  `--dry-run` "writes nothing, not even the store root" guarantee.
- `ahm store path` in `project` mode resolves the store without the records
  living in it; the lock must not turn that read-only inspection into a store
  write outside the documented exceptions.

## Acceptance

- A test that fails before the change: two writers that interleave on the
  registry or the state file both keep their observation. Use a deterministic
  interleaving (a test hook in the style of `workflowLockClaimHook`) rather than
  racing goroutines, so the test cannot flake.
- No interleaving of `store path` and `task create` can lower the persisted
  `next_id`.
- `store path` stays idempotent: a repeated run rewrites nothing and moves no
  modification time.
- Project mode stays byte-identical, `--dry-run store path` still creates
  nothing, and an unknown store format version is still refused with exit 1.
- `just ci` passes.

## Comments

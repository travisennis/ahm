# Cache workflow metadata reads for the life of a command

## Problem

`readMetadata` has around 20 call sites and is uncached. Each call performs two
`os.Stat` calls via `metadataReadRelPath`, a `ReadFile`, and a
`json.Unmarshal`. It is invoked per-validator (`validation.go:166`, `:237`,
`:664`, `:775`) and on every path resolution (`workflow_paths.go:27`).

Beyond the redundant I/O, the correctness angle matters more: different
validators within a single command can observe *different* metadata if the file
changes mid-run, so one `ahm status` or `ahm doctor` invocation can report
findings derived from two different configurations.

`workflowPaths` already carries a `pathsCache` from task 203; metadata deserves
the same treatment and the same scope.

## Relevant Files

- `internal/ahm/install.go` — `readMetadata`, `metadataReadRelPath`.
- `internal/ahm/workflow_paths.go:27` — `pathsCache`, the pattern to follow.
- `internal/ahm/validation.go:166`, `:237`, `:664`, `:775` — per-validator reads.

## Fix Direction

Memoize metadata on the `app` for the duration of a command, mirroring
`pathsCache`: one read, one unmarshal, one observed configuration per
invocation. Invalidate alongside the existing cache invalidation points so
commands that write metadata (`init`) still observe their own writes.

Return a copy from the cache so a caller cannot mutate the cached value.

## Acceptance Notes

- [ ] Metadata is read and unmarshalled at most once per command for read-only
      paths.
- [ ] A test proves all validators in one run observe the same metadata even if
      the file changes mid-run.
- [ ] Commands that write metadata observe their own writes; existing install
      tests pass unchanged.
- [ ] Cached metadata cannot be mutated by a caller.
- [ ] `just ci` passes.

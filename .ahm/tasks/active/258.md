# Design a resolvable link scheme for workflow record references

## Problem

Workflow records and committed project documents reference each other by
relative filesystem path. `validateMarkdownLinks`
(`internal/ahm/validation.go:774`) resolves those inside task and ADR bodies and
emits `markdown_link_missing` when a target is absent.

Relative paths are fragile in both directions. A record that moves between
lifecycle buckets breaks its outbound links, and a committed document that cites
a record by path breaks when that record is archived or renamed, so the
project's own decision history depends on path stability that nothing enforces.

## Why now

This is a standing correctness problem for the two surviving record families
(tasks and ADRs), and every new record adds another relative path to the pile.
The scheme has to be designed before more record bodies and project documents
adopt the current convention.

## Direction

- Define a resolvable reference syntax that `ahm` interprets, rather than
  relying on filesystem-relative paths. Both directions need an answer:
  record-to-project and project-document-to-record.
- Decide whether one form covers both directions or each gets its own, and be
  explicit about which references each form covers.
- Teach `validateMarkdownLinks` the scheme so resolution and the
  `markdown_link_missing` finding stay meaningful. The finding code is a
  compatibility surface — see `ARCHITECTURE.md` — so changing its behavior needs
  care.
- Record templates teach the current convention and would need updating.
- Existing records and ADRs use relative paths today. Decide whether they are
  migrated, supported indefinitely alongside the new scheme, or reported by
  `doctor` as drift.

## Decisions to make

- Scheme syntax, and whether one form covers both directions or each gets its
  own.
- Whether references resolve by stable identity (task or ADR id) or by path
  relative to a record root. Identity survives lifecycle moves; paths are more
  obvious to a human reader.
- Backward compatibility for the relative links already in the repository.

## Acceptance criteria

- A record can reference a project file, and a project document can reference a
  record, using a form that survives the record moving between lifecycle
  buckets.
- Validation resolves the new scheme and reports genuinely broken references
  without false positives on valid ones.
- Existing relative links behave per the compatibility decision, documented
  rather than incidental.
- Templates and project documentation teach the scheme.

## Verification

`just ci` plus `CONTRIBUTING.md` policy. Include validation tests for
resolvable, broken, and legacy-relative references in both directions.

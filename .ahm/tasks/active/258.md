# Design a resolvable link scheme for workflow record references

## Problem

Workflow records and committed project documents reference each other by
relative filesystem path. `validateMarkdownLinks`
(`internal/ahm/validation.go:774`) resolves those and emits
`markdown_link_missing` when a target is absent — a warning currently visible in
this repository's own `ahm prime` output for
`.ahm/exec-plans/completed/172-committed-ahm-records.md:10`.

Relative paths are fragile in both directions. A record that moves between
lifecycle buckets breaks its outbound links, and a committed document that cites
a record by path breaks when that record is archived or renamed. ADR 015 cites a
research note this way, so the project's own decision history depends on path
stability that nothing enforces.

## Why now

This is a standing correctness problem independent of any storage change.

It also becomes structural under the external-store design in
`.ahm/research/topics/external-store-workflow-records.md`, where records leave
the repository entirely and relative paths between records and project files
stop being expressible at all. Designing the scheme now means that design
inherits a solved problem, and the project gets more durable references either
way.

## Direction

- Define a resolvable reference syntax that `ahm` interprets, rather than
  relying on filesystem-relative paths. Both directions need an answer:
  record-to-project and project-document-to-record.
- Records already use `[[name]]` for research-note cross-references; consider
  whether the new scheme extends that idea or sits beside it, and be explicit
  about which references each form covers.
- Teach `validateMarkdownLinks` the scheme so resolution and the
  `markdown_link_missing` finding stay meaningful. The finding code is a
  compatibility surface — see `ARCHITECTURE.md` — so changing its behavior needs
  care.
- Record templates and `ahm context *` guidance both teach the current
  convention and would need updating.
- Existing records and ADRs use relative paths today. Decide whether they are
  migrated, supported indefinitely alongside the new scheme, or reported by
  `doctor` as drift.

## Decisions to make

- Scheme syntax, and whether one form covers both directions or each gets its
  own.
- Whether references resolve by stable identity (task id, record name) or by
  path relative to a record root. Identity survives lifecycle moves; paths are
  more obvious to a human reader.
- Backward compatibility for the relative links already in the repository.

## Acceptance criteria

- A record can reference a project file, and a project document can reference a
  record, using a form that survives the record moving between lifecycle
  buckets.
- Validation resolves the new scheme and reports genuinely broken references
  without false positives on valid ones.
- Existing relative links behave per the compatibility decision, documented
  rather than incidental.
- Templates and context guidance teach the scheme.
- The existing `markdown_link_missing` finding in this repository is either
  resolved or explicitly out of scope with a reason.

## Verification

`just check` plus `CONTRIBUTING.md` policy. Include validation tests for
resolvable, broken, and legacy-relative references in both directions.

# Design an ahm config command for workflow settings

## Summary

Repository-scoped settings are configurable only by hand-editing
`.ahm/config.json`. After ADR 022 the surface is small: the preserved version
field, `strict_acceptance`, and the managed-file hash map, plus preserved
unknown fields. Corrupt metadata deliberately fails commands loudly, so a
validating `ahm config` surface could reduce editing risk, but its key grammar
and ownership boundary require a durable decision first. The original two-key
proposal was written against commit `ff15056` and is retained only as
historical context.

## Evidence

- `internal/ahm/install.go` — the `metadata` type: the preserved version
  field, `strict_acceptance`, `files`, and the unknown-key passthrough, plus
  the read and atomic write helpers around it.
- `docs/references/workflow-spec.md` — documents current `.ahm/config.json`
  ownership and supported settings.

## Fix Direction

Produce an ADR that selects a bounded configuration command model for the
reduced surface. Compare a typed fixed-key surface with a whole-document
edit/validate workflow, and choose the smallest model that justifies a
command at all. The decision must preserve unknown fields, reject writes to
ahm-owned `version` and `files` metadata, validate values before atomic
replacement, and define text/JSON/plain plus dry-run behavior. After
acceptance, create implementation tasks rather than silently reviving the
obsolete two-key scope.

## Decision

This task produces the prerequisite ADR; it does not implement the command.
The ADR must choose the mutable-key surface and addressing model, after which
separate implementation tasks will carry the selected behavior.

## Acceptance Notes

- [ ] An accepted ADR defines the supported configuration command model for
      the `.ahm/config.json` keys that survive ADR 022.
- [ ] Supported mutable keys, key syntax, value validation, unknown-field
      preservation, and prohibited ahm-owned keys are explicit.
- [ ] Missing/corrupt metadata, dry-run, output modes, exit codes, and atomic
      write behavior are specified.
- [ ] Security and safety constraints prohibit arbitrary command execution or
      implicit metadata creation/reset.
- [ ] Concrete implementation and documentation tasks are created after the
      decision is accepted.
- [ ] `just ci` passes for the ADR/documentation change.

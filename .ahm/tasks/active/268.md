# Never reissue a deleted child task ID in the home store

## Summary

Top-level task IDs are protected in the home store by the `next_id` counter
267d added, but a child ID is not. `nextChildTaskIDForPaths` in
`internal/ahm/task_create.go` scans the parsed records and the record directory
for the first unused letter under the parent, so deleting `137d` returns that
letter to the pool: the next child under 137 is also `137d`.

In a committed project Git history is the evidence that a letter was used; a
store has none, so a note, a `depends_on` entry, or a comment that names the
deleted child silently comes to mean a different task. That is the same failure
the top-level counter exists to prevent.

267d deliberately kept the child rules unchanged, and the gap is recorded in
`docs/exec-plans/active/267-home-store-for-task-records.md` (Surprises &
Discoveries, 267d) and in ARCHITECTURE.md, which states that a deleted child's
letter can be reissued in both layouts.

## Detail

- The scan and its 26-child limit live in `nextChildTaskIDForPaths`
  (`internal/ahm/task_create.go`).
- The store counter, its write path, and the hook that deliberately ignores
  child IDs (`persistTaskIDCounter`) live in `internal/ahm/task_id_counter.go`.
- The persisted shape is `projectState` in `internal/ahm/store.go`, in the
  store's `project.json` (`storePaths.statePath()`), written through
  `writeOwned` and never lowered.
- A per-parent mark needs a shape decision: a map from parent number to the
  highest used letter, a map to the set of used letters, or one
  highest-suffix-per-parent value keyed by the parent's padded ID. Only the
  store needs it; project mode keeps the scan and its Git history.
- Existing behavior to preserve: the 26-child error message, the bucket scan,
  zero-padded IDs, `--parent` validation (only top-level tasks can be parents),
  and byte-identical project-mode output.

## Acceptance

- A test that fails before the change: create a parent, create a child, delete
  the child's record by hand, create another child under the same parent; the
  second child does not reuse the deleted child's ID.
- The mark is persisted in the store's state file with the same monotonic rule
  as `next_id` (raised after the record is written, never lowered, unchanged by
  a dry run).
- A store whose state file holds no suffix mark self-heals from the children
  present, as top-level allocation does.
- The 26-child limit and its error message are unchanged, and a parent's second
  child is still the next free letter after the ones present.
- Project mode stays byte-identical, and an existing store keeps working
  without a migration.
- `just ci` passes.

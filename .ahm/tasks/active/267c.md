# Read and write task records in the home store

## Summary

Make the store real: task commands read and write records under the records
root, indexes split across the two roots, `prime` and `status` report the
store, and validation reports drift when the mode and the records disagree.
The default mode stays `project` until 267f, so this milestone changes behavior
only for a configuration that already names `home`.

Configuration: add `TasksLocation` to `metadata` in `internal/ahm/install.go`,
in both the hand-written `MarshalJSON` and the `UnmarshalJSON` delete list so
it is never preserved as an unknown field. Add

    func resolveTaskLocation(meta metadata, configExists bool) taskLocation

A missing key means `project`; a repository with no configuration is `home`,
which 267f turns on. Wire `resolveWorkflowPaths` into `app` after root
detection.

Install: when the mode is `home`, `install()` creates the store project
directory (`tasks/{active,completed,cancelled}`, `.lock`, and the store's
managed `.gitignore`) and never creates `.ahm/tasks/`. Reuse the existing
exists-but-not-a-directory error from `ensureWorkflowDirs`.

Indexes: in `indexWritesForPaths`, the four task indexes are written under the
records root and `docs/adr/index.md` stays under the project root. Keep index
content byte-identical; a task index link such as `active/001.md` must keep
resolving because the store mirrors the in-project layout.

Validation: `workflowMarkdownFilesForPaths` already enumerates both families
from resolved paths, so it should follow the records root. Add a read-only
finding, `task_records_in_project`, reported when the mode is `home` and task
records still exist under `.ahm/tasks/`, and a finding for a `home` project
whose store directory is missing or unreadable. Update
`validateMarkdownFileLinks` to resolve a target against the record's own
directory first and, only if that does not exist, against the record's logical
in-project directory, per ADR 023.

Output: `prime` and `status` report `store: {root, key, kind, location}` and
display store paths with the `store:` prefix. Keep `project` mode output
byte-identical. 267b left the remaining path *display* on `relPath(root, …)`:
validation findings, `validateTaskBuckets` messages, the `collectTasksForPaths`
parse-error message, `Task.Path` in JSON, the `checkDuplicateTaskID` and
`checkTaskDepsNotDuplicated` messages, the dry-run `move` and unblock preview
payloads in `task_status.go`, and lock-timeout errors all relativize a record
path against the project root. Switch them to `displayPath` in this milestone,
so a record path is never rendered against the wrong root, and make
`displayPath` the single label helper for record paths. Confirm the delete side
too: `task_status.go` removes a vacated record path directly with `os.Remove`,
with no owned-root check.

Store `.gitignore`: ADR 023 and the ExecPlan's Idempotence section say the
store root holds the managed `.gitignore` that ignores `registry.json`, while
the ExecPlan's Artifacts layout puts it at `<store>/projects/<slug>-<hash>/`.
267b's `ownedRoots` is the project root plus the store's project directory, so
a store-root write is refused. Decide where the file goes here — placing it per
project needs no change, while ignoring `registry.json` needs the store root
admitted as an owned root — and hand the ADR wording to 267h.

## Acceptance

- With `tasks_location: home`, `ahm task create`, `list`, `show`, `complete`,
  and `dep` operate entirely in the store and write nothing under
  `.ahm/tasks/`.
- With the key absent, the entire existing suite passes with byte-identical
  output and layout; this is the guard for existing repositories and must not
  be weakened.
- `ahm doctor` reports `task_records_in_project` when a record is left in the
  project while the mode is `home`.
- A task record whose body links to `../../../docs/adr/<n>-<slug>.md` still
  validates after a move, and a link to a sibling task still validates.
- `just ci` passes.

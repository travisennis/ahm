# Create audit findings in a single locked batch

## Problem

`createAuditTasks` calls `taskCreateParsed` once per finding. Each call acquires
the workflow record lock, regenerates *every* index, and runs full
post-mutation validation. Twenty findings means twenty lock acquire/release
cycles, twenty full index regenerations, and twenty validation passes.

It is also non-atomic in a way the command does not report: a failure at finding
*k* returns an error with *k-1* tasks already created and the audit summary
discarded, so the operator loses the record of what the audit found and has to
reconcile partially-created tasks by hand.

This is the same failure shape as task 229 (`applyGroomVerdicts`), in the other
delegated command.

## Relevant Files

- `internal/ahm/audit.go:284-303` — `createAuditTasks`.
- `internal/ahm/tasks.go` — `taskCreateParsed`, lock acquisition, index
  regeneration.
- `internal/ahm/task_groom.go` — `applyGroomVerdicts`, the parallel case
  tracked by task 229.
- `internal/ahm/audit_test.go` — audit coverage.

## Fix Direction

Introduce an internal batch-create path that takes the record lock once,
allocates ids and writes all task records, then regenerates indexes and runs
post-mutation validation once. Keep `taskCreateParsed` as the single-task entry
point over the same primitive so id allocation and front matter rendering do not
fork.

Also drop the `a.out`/`a.in` swapping used to capture allocated ids — a batch
primitive that returns the created ids removes the need to reparse them out of
captured stdout.

On failure, report which findings were created and which were not, and still
emit the audit summary; align the semantics with whatever task 229 settles for
grooming so the two delegated commands behave the same way.

## Acceptance Notes

# Guard tests against resolving paths outside their temp directory

## Problem

Every path `ahm` touches today derives from the detected repository root. The
test suite uses `t.TempDir()` in 388 places, and the codebase contains no
reference to `XDG_DATA_HOME`, `UserHomeDir`, or `HOME` anywhere. That absence is
what structurally prevents a mutating test from escaping its sandbox — not any
deliberate guard.

That property is currently free, undocumented, and unenforced. Nothing fails if
a future change introduces a home-directory or environment-derived path, and the
first symptom of such a bug in a mutating test would be damage to a developer's
real workflow records.

## Why now

Cheap hardening on its own, and a hard prerequisite for the external-store
design in `.ahm/research/topics/external-store-workflow-records.md`, which
introduces the first genuine home-directory dependency. The research note calls
for this to land before store resolution rather than alongside it, so the guard
exists before the hazard does.

## Direction

- Add a test helper that asserts any resolved workflow path lies within the
  test's temp directory, and fail loudly otherwise.
- Prefer a mechanism that applies broadly rather than one each test must
  remember to call. A `TestMain` hook, or a guard inside the shared test
  repository setup helper, is likelier to hold over time than an opt-in
  assertion.
- If an environment override for a store root is introduced later, this guard
  is what ensures every test sets it.
- Do not weaken the existing root-derived path model to accommodate the guard;
  the guard exists to protect that model.

## Acceptance criteria

- A test that resolves a workflow path outside its temp directory fails with a
  clear message naming the offending path.
- The guard is active by default for mutating tests rather than opt-in.
- The full suite passes unchanged, confirming no current test violates it.
- The invariant is documented where a future contributor will encounter it —
  `docs/guides/testing.md`, and `docs/guardrails/safety-and-permissions.md`
  which owns the out-of-repository path failure mode.

## Verification

`just check`. Add a deliberately violating test, confirm it fails with the
intended message, then remove it or keep it as a negative test if the harness
supports asserting failure.

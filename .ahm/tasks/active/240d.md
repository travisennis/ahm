# Decide durable research metadata enforcement

## Summary

After the durable-research creation threshold is clear, decide whether ahm should keep research metadata and lifecycle guidance advisory or establish a mechanically enforced record contract with supporting commands.

## Problem

`ahm context research` currently presents a status, date, relationship, and confidence header only "when useful." Existing code can consume conventional dates for stale-inbox reporting, while indexes and manual file operations intentionally remain lightweight. Making metadata normative or adding `research create`, `promote`, or `archive` commands could improve consistency, but it could also create a file-format compatibility and migration burden disproportionate to the value.

## Decision Work

Inventory the current source of truth for research discovery, indexing, stale-note dates, status vocabulary, storage layouts, manual moves, and upgrade compatibility. Then compare at least these options:

1. Keep the current guidance-only header and manual lifecycle.
2. Require a minimal metadata contract only for durable notes while leaving raw inbox captures lightweight.
3. Add validation for a minimal contract without adding mutation commands.
4. Add focused lifecycle commands only where they enforce a settled contract and materially reduce unsafe manual work.

Evaluate compatibility with existing `.ahm/research/` and legacy `.agents/.research/` records, migration behavior, generated indexes, `status` and `doctor`, source ownership, and whether front matter or the documented plain header should be canonical. Avoid designing commands before identifying an invariant they need to protect.

If the selected option changes a durable file-format or CLI contract, create and accept an ADR before implementation and materialize separately scoped implementation tasks. Do not implement the selected option in this decision task.

- [ ] The decision distinguishes raw inbox captures from synthesized durable research.
- [ ] Required metadata, if any, has explicit semantics, ownership, backward compatibility, and migration behavior.
- [ ] Lifecycle commands are proposed only for settled invariants that cannot be handled safely and clearly through existing file operations.
- [ ] A durable contract change is recorded in an accepted ADR; a guidance-only decision records why no ADR or implementation is needed.
- [ ] Any implementation is represented by follow-up tasks with concrete behavioral acceptance criteria and dependencies.
